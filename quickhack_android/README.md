# Packing Integrity Checker

Android packing verification client for QuickHack ERP/WMS.

## Secure operating model

- The app logs in through `POST /api/auth/login`.
- The app keeps the QuickHack session cookie in memory only. It is not written to disk.
- Device provisioning starts only from a ready physical USB ADB target selected in QuickHack.
- The app creates a P-256 Android Keystore key and proves possession by signing the provisioning request.
- The device token is generated by the app and encrypted with Android Keystore using the normalized server origin as AES-GCM AAD.
- Packing checks call only `POST /api/mobile/packing-check`.
- Packing checks send the scanned barcode values in the order they were scanned, app install ID, and encrypted-registration device token.
- QuickHack performs the comparison on the server and returns only the minimal result.
- Every check is written to `employee_activity_logs` as `MOBILE_PACKING_CHECK`.
- Android backup is disabled.
- Cleartext HTTP is blocked. Use HTTPS or a company VPN/reverse proxy.

## Device registration

1. In QuickHack, open user account management.
2. Enable `포장 검수 앱 접근 허용` for the target account and save it.
3. Connect the phone with ADB and refresh the ADB device list.
4. Register the selected physical USB device to the target account.
5. QuickHack sends a short-lived provisioning request directly to that exact device with `adb -s`.
6. Log in on the Android app. The app signs the request and completes registration without displaying or typing an activation code.

QuickHack stores only an HMAC hash of the ADB serial. Runtime packing checks do not depend on Android exposing the hardware serial.

## Server API

Activation request (created and signed by the app):

```json
{
  "deviceId": 123,
  "registrationRevision": 0,
  "provisioningToken": "short-lived USB-delivered secret",
  "appInstanceId": "origin-bound app install id",
  "deviceToken": "app-generated random token",
  "devicePublicKeySpki": "P-256 SPKI base64",
  "signature": "SHA256withECDSA signature"
}
```

The server returns the same device token only after the signature and account session are verified. Repeating the exact request after a lost response is idempotent.

Packing request:


```json
{
  "scannedValues": ["PG or IMEI", "order/shipment/invoice barcode"],
  "appInstanceId": "origin-bound app install id",
  "deviceToken": "server-issued device token"
}
```

Response:

```json
{
  "ok": true,
  "data": {
    "matched": true,
    "code": "MATCH",
    "message": "Same order and model."
  }
}
```

Mismatch responses return `matched: false` and a code such as:

- `DEVICE_NOT_FOUND`
- `ORDER_NOT_FOUND`
- `ORDER_NOT_ALLOCATED`
- `ORDER_DEVICE_MISMATCH`
- `MODEL_MISMATCH`

## Scan flow

1. Open the app and log in to the QuickHack HTTPS server.
2. Connect the phone by USB and start registration from QuickHack, then log in to the app.
3. After login, the app enters signal mode and opens the camera scanner automatically.
4. The worker scans PG/IMEI, order/shipment/invoice, and future component barcodes in any order.
5. The app displays scanned values in large text.
6. When enough values are present, QuickHack decides from DB data.
7. A valid match fills the screen green.
8. A mismatch fills the screen red and triggers warning tone and vibration.
9. The screen resets automatically and repeats.

The operational screen intentionally avoids normal buttons. Long press the signal screen to return to setup mode.

## Android Studio

1. Open the `quickhack_android` folder in Android Studio.
2. Let Android Studio install or sync the required Gradle and Android SDK components.
3. Configure a QuickHack HTTPS endpoint.
4. Enter that endpoint in the app, for example `https://quickhack.company.local`.

For local development, use an HTTPS reverse proxy or tunnel in front of the QuickHack dev server. The release app intentionally rejects `http://` URLs.
