# QuickHack 포트폴리오 핵심 설득 초안

## 1. 이 프로젝트가 증명하려는 것

QuickHack은 AI를 이용해 ERP 화면을 빠르게 만든 프로젝트가 아니다.

현장에서 발견한 모호한 문제를 데이터의 의미, 상태 전이, 실패 경계, 복구 책임, 검증 기준으로 구체화하고, AI가 그 경계 안에서 안정적으로 구현하도록 작업을 설계한 프로젝트다.

> **나는 AI에게 기능 구현만 맡긴 것이 아니라, 자동화해도 되는 판단, 보수적으로 멈춰야 하는 상태, 사람이 책임져야 하는 복구, 애초에 만들지 않아야 할 기능을 구분하고 그 경계를 시스템으로 구현했다.**

여기에 한 가지 역량이 더해진다.

> **복잡한 기능을 의존성 기반 작업 지도로 분해하고, 충돌하지 않는 작업을 병렬화해 구현 속도와 통합 안정성을 함께 관리했다.**

AI가 코드 생성에 크게 기여한 것은 사실이다. 하지만 AI는 다음 질문에 대한 답을 스스로 책임질 수 없다.

- 같은 숫자가 화면마다 다를 때 무엇을 정본으로 삼을 것인가
- 결과가 불명확한 외부 쓰기를 다시 실행해도 되는가
- 개인정보를 어느 업무 상태에서 삭제할 수 있는가
- 자동 복구가 오히려 위험해지는 시점은 언제인가
- 과거 데이터를 정확히 복원할 근거가 없을 때 무엇을 표시할 것인가
- 여러 AI 작업이 동시에 같은 스키마와 계약을 수정하지 않게 하려면 어떻게 나눌 것인가

QuickHack에서 내가 맡은 역할은 이 질문에 답하고, 답을 SDD와 코드 경계, 작업 순서, 테스트로 연결하는 것이었다.

## 2. 개발 방식의 변화

### 초기 방식

초기에는 현장에서 필요한 기능을 발견할 때마다 AI에게 구현을 요청했다.

```text
기능 필요 발견
→ 구현 요청
→ 코드 생성
→ 동작 확인
```

개별 기능은 빠르게 만들어졌지만 프로젝트가 커질수록 문제가 생겼다.

- 같은 업무 용어를 화면마다 다르게 계산했다.
- AI가 명시되지 않은 예외를 임의의 정상 흐름으로 채웠다.
- 외부 API 실패를 단순 재시도로 처리할 위험이 생겼다.
- 현재 상태와 변경 이력이 섞였다.
- 뒤늦게 발견한 조건 때문에 기존 기능을 반복 수정했다.
- 서로 다른 작업이 같은 공유 계약과 스키마를 동시에 수정했다.

### 전환한 방식

이후 구현 전에 다음 지도를 먼저 만들었다.

1. **업무 지도**  
   실제 사용자가 무엇을 판단하고 어떤 결과를 필요로 하는가

2. **데이터 지도**  
   어느 데이터가 현재 상태이고 어느 데이터가 증거와 이력인가

3. **상태 지도**  
   정상, 실패, 결과 불명, 복구 대기, 수동 확인을 어떻게 구분하는가

4. **실행 지도**  
   UI, API, service, transaction, worker, 외부 시스템이 어떻게 연결되는가

5. **작업 지도**  
   어떤 계약이 선행되어야 하고 어떤 작업을 동시에 진행할 수 있는가

6. **검증 지도**  
   완료를 코드 존재가 아니라 어떤 테스트와 데이터 불변식으로 증명할 것인가

AI는 이 지도 안에서 코드 작성, 반복 구현, 테스트 초안, 리뷰와 문서화를 수행했다. 나는 지도에 포함될 제품 결정과 금지 조건을 정하고, 결과가 실제 코드와 일치하는지 검증했다.

## 3. 대표 사례 1 — 재고 숫자가 아니라 숫자의 근거를 재설계하다

### 문제

기존 재고 수불 현황은 `SKU × 재고 상태`를 반복 행으로 표시하고, 사용자가 확인하지 않은 movement도 최초 응답에 최대 500건까지 포함했다.

입고 차수 화면과 통계 대시보드는 기대 수량, 연결 수량, 매입처 반품, 정상 입고 대상을 서로 다른 방식으로 계산했다. 날짜가 다른 동일 차수를 문자열로 결합하거나, 기대 수량이 없을 때 의미가 다른 합계를 fallback으로 사용하면 같은 업무 용어가 화면마다 다른 숫자를 보여줄 수 있었다.

### 내가 내린 판단

- `latest inbound` 판정과 입고 대조 공식을 서버 공통 서비스에 한 번만 정의한다.
- 정상적인 재고 0과 원장 미생성 또는 부분 손상을 같은 0으로 표현하지 않는다.
- movement는 사용자가 정확한 balance를 선택한 뒤에만 조회한다.
- 매 요청마다 전체 원장 audit를 실행하지 않는다.
- 조회 화면을 위해 새로운 통계 snapshot worker를 만들지 않는다.
- 현재 구조로 해결할 수 있으므로 신규 테이블과 backfill을 추가하지 않는다.

### 설계 전환

원장 가용성을 다음 상태로 분리했다.

- `READY`: 원장과 movement 근거가 정상적으로 존재
- `EMPTY`: 정상적인 재고 0
- `INITIALIZATION_PENDING`: 원장 초기화가 아직 완료되지 않음
- `PARTIAL`: balance, movement 또는 SKU 근거가 일부 불완전함

메인 matrix는 수량 분포와 compact 대조 결과만 제공한다. movement는 exact balance 선택 이후 cursor API로 지연 조회한다. 상세 조회가 실패해도 메인 matrix는 유지한다.

전체 불변식 검사는 기존 audit worker가 담당하고, 사용자 조회는 가벼운 availability 판정만 수행한다.

### AI 작업 통제

AI에게 단순 UI 개편이 아니라 다음 계약을 먼저 제공했다.

- 세 화면이 같은 reconciliation service를 사용할 것
- 기대 수량을 다른 합계로 추정하지 말 것
- 정상적인 0과 근거 부족을 타입과 표시에서 구분할 것
- 서로 다른 balance의 movement를 하나의 원인처럼 합치지 말 것
- 최초 응답에서 movement 전체를 선조회하지 말 것
- 서버 계약과 UI 전환을 별도 PR로 나눠 단독 병합 가능성을 유지할 것

### 구현과 검증

- 공통 latest inbound loader와 reconciliation service
- matrix 및 availability 계약
- balance별 movement cursor API
- 세 화면의 공통 계산 연결
- legacy movement 선조회 제거
- 전용 fixture, TypeScript 검사와 전체 검증

### 이 사례가 증명하는 것

> **화면에 숫자를 추가한 것이 아니라, 숫자가 신뢰될 수 있는 증거 구조와 조회 비용의 경계를 다시 설계했다.**

## 4. 대표 사례 2 — 개인정보 삭제를 날짜가 아닌 업무 수명주기로 바꾸다

### 문제

기존 개인정보 만료 worker는 주문의 마지막 동기화 시각인 `coupang_order_raw.updated_at`을 기준으로 90일을 계산했다.

이 방식에서는 다음 문제가 발생할 수 있었다.

- 장기간 갱신되지 않은 미완료 주문이 너무 일찍 마스킹된다.
- 완료 주문이 반복 동기화되면 `updated_at`이 계속 갱신되어 영구 보존될 수 있다.
- 주문 원문을 마스킹해도 합포장, 배송지 변경, 송장 재발급 테이블에 복제된 이름·전화·주소가 남는다.
- 실제로 아무 작업도 하지 않는 worker가 성공 상태로 기록된다.

### 내가 내린 판단

- 개인정보 보존 시계는 동기화 시각이 아니라 배송·반품·교환의 실제 종결 근거로 계산한다.
- 진행 중이거나 상태가 불명확한 claim이 있으면 보존 시계를 중지한다.
- 종결 근거가 없으면 삭제하지 않는다.
- 주문 원본만이 아니라 배송 실행 과정에서 생성된 파생 snapshot 전체를 개인정보 inventory로 관리한다.
- 공유 합포장이나 진행 중 작업이 있으면 보수적으로 정리를 연기한다.
- 배송 개인정보와 문의·분쟁·보증·거래 증거는 서로 다른 보존 목적으로 분리한다.
- 실제 작업을 하지 않는 no-op worker를 제거한다.

### 설계 전환

주문·배송번호별 개인정보 lifecycle projection에 다음 근거를 분리해 저장하도록 설계했다.

- 최초 배송 완료 근거
- 진행 중 claim 수
- 가장 늦은 claim 종결 시각
- 실제 90일 보존 시작 시각
- 판단 근거
- 파생 개인정보 정리 완료 시각

일일 worker는 이 lifecycle에서 만료된 subject만 읽는다. 하나의 subject에 연결된 원본과 파생 snapshot은 같은 transaction에서 처리하고, 중간 실패나 lease 상실이 발생하면 완료 marker까지 함께 rollback한다.

공유 package group의 다른 구성원이 아직 보존 대상이 아니거나 관련 작업이 진행 중이면 공유 snapshot은 보존하고 deferred 사유를 기록한다.

### AI 작업 통제

- `updated_at`을 보존 근거로 재사용하지 말 것
- active 또는 unknown 상태를 임의로 terminal로 해석하지 말 것
- 원문이 남을 수 있는 모든 파생 저장소를 먼저 조사할 것
- 마스킹 완료 marker는 모든 in-scope copy가 정리된 뒤에만 기록할 것
- 이미 마스킹된 과거 원문을 DB에서 임의 복원하지 말 것
- 문의와 감사 기록을 배송 개인정보 90일 정책에 억지로 포함하지 말 것

### 이 사례가 증명하는 것

> **개인정보를 많이 삭제한 것이 아니라, 지워도 되는 시점과 지워서는 안 되는 상태를 업무 생명주기로 모델링했다.**

## 5. 대표 사례 3 — 자동화가 멈춰야 할 조건을 설계하다

### 문제

자동화는 반복 작업을 줄일 수 있지만, 모든 실패와 지연을 자동 재실행으로 처리하면 새로운 비용과 위험을 만든다.

- 이미 완료된 무거운 통계 계산을 다시 실행할 수 있다.
- 서버 중단 기간의 모든 날짜를 복구하려다 시작 부하가 커질 수 있다.
- 외부 쓰기가 이미 반영됐는데 timeout만 발생한 경우 동일 요청을 중복 전송할 수 있다.
- 결과가 불명확한 출력이나 복구를 시스템이 임의로 재개할 수 있다.

### 내가 내린 판단

#### 통계 snapshot

- 같은 cutoff의 완료본이 있으면 예약 실행은 계산 전에 건너뛴다.
- 늦게 동기화된 사실을 반영해야 할 때만 LEADER가 수동 재계산한다.
- 서버 복귀 시 누락된 모든 날짜를 자동 backfill하지 않고 최신 cutoff 한 건만 보충한다.
- 네 통계는 병렬 계산하지 않고 순차 실행해 SQLite와 Node event loop의 순간 부하를 제한한다.
- 하나의 daily worker를 위해 범용 schedule schema와 관리 UI를 새로 만들지 않는다.
- 통계 GET 요청이 무거운 worker를 즉시 실행하지 않는다.

#### 외부 쓰기와 물리 작업

- 성공 응답만으로 외부 반영 완료를 확정하지 않는다.
- timeout과 연결 종료를 명확한 실패로 단정하지 않는다.
- 결과가 불명확하면 동일 쓰기 재전송보다 읽기 검증을 먼저 수행한다.
- 끝까지 확정할 수 없으면 `REVIEW_REQUIRED`로 사람에게 넘긴다.
- 결과가 불명확한 송장 출력은 자동 재출력하지 않는다.
- 강제 종료나 불확실한 복구 뒤에는 자동 재시작하지 않고 운영자 확인을 요구한다.

### 설계 원칙

```text
자동 복구 가능
→ 멱등성과 결과 검증이 보장되는 범위에서 재실행

결과 불명
→ 상태 조회와 증거 대조

그래도 확정 불가
→ 자동화 중지
→ 운영자에게 판단 위임
```

### 이 사례가 증명하는 것

> **자동화율을 높이는 것보다, 자동화 비용이 정당한 순간과 사람이 책임져야 할 순간을 구분했다.**

## 6. 대표 사례 4 — 의존성을 설계해 AI 작업을 병렬화하다

### 문제

AI 에이전트를 여러 개 사용한다고 자동으로 구현 속도가 빨라지는 것은 아니다. 여러 작업이 같은 스키마, 공유 타입, worker registry와 테스트 설정을 동시에 수정하면 코드 작성 시간보다 충돌 해결과 재검증 비용이 커진다.

### 내가 내린 판단

병렬화 여부를 기능 이름이 아니라 실제 코드 소유권과 데이터 계약으로 결정했다.

- 같은 파일·심볼·DB 상태·오류 계약을 수정하는 작업은 같은 lane에서 직렬화한다.
- 소유 영역과 검증 경계가 분리된 작업만 별도 branch와 worktree에서 병렬로 진행한다.
- `package.json`, Prisma schema·migration, worker registry·keys, 공통 SDD는 integration owner가 단독 관리한다.
- 각 lane은 고유한 테스트를 독립 실행하고 공통 `verify` 연결은 통합 단계에서 한 번 수행한다.
- 병렬 결과가 만나는 통합 PR에서 migration 순서, 공유 계약, 타입 검사와 전체 회귀를 다시 검증한다.
- 기반 계약, 서버 구현, UI 연결, 최종 전환을 PR 단계로 나눠 각 단계가 단독 병합돼도 기존 동작을 깨지 않게 한다.

### 실제 작업 구조

코드리뷰 후속 작업에서는 남은 15개 항목을 11개 lane으로 분리했다.

- 같은 TOTP 상태를 수정하는 작업은 하나의 lane 안에서 순차 처리
- 로그인 timing, 모바일 등록, 민감 action처럼 상위 도메인은 같아도 소유 서비스와 DB 상태가 다른 작업은 병렬 처리
- 로젠 추적, backup 암호화, QHKEY, 로컬 출력 spool처럼 외부 integration 파일이 겹치지 않는 작업은 별도 wave로 처리
- trace 수명주기처럼 공통 registry나 schema 결합이 필요한 작업은 integration owner가 최종 반영

실제 병렬 구현 결과는 통합 tree와 다시 대조했다. 구현 내용은 유지하면서 migration 순서만 정렬하고, 전용 회귀, TypeScript, production build와 staging 검증을 수행했다.

### 안전한 병렬화와 런타임 병렬화의 구분

개발 작업은 독립성이 확보된 경우 병렬화했지만, 운영 코드의 무거운 통계 계산은 순간 부하를 이유로 순차 실행했다.

이 구분은 “병렬이면 항상 빠르다”가 아니라 다음 원칙을 보여준다.

> **병렬화는 목적이 아니라, 충돌 비용과 실행 부하를 포함해 총 작업 시간을 줄일 때 사용하는 설계 선택이다.**

### 이 사례가 증명하는 것

> **복잡한 설계를 실행 가능한 작업 그래프로 변환하고, 여러 AI 작업이 동시에 진행돼도 전체 계약이 흔들리지 않도록 통합 경계를 관리했다.**

### SDD 근거

- `specs/features/codebase-review-hardening/impact.md`의 P2 병렬 작업 경계
- `specs/features/codebase-review-hardening/impact.md`의 병렬 구현 통합 기록
- `specs/features/statistics-completion/system_design.md`의 PR 1·2 병렬 경계
- `specs/features/inventory-ledger-matrix/system_design.md`의 단계적 서버·UI 전환

정확한 소요시간 비교 기록은 없으므로 “개발 속도 N배” 같은 수치는 사용하지 않는다. 대신 독립 작업의 동시 진행, 공통 파일 충돌 방지, 단독 병합 가능성, 통합 검증 비용 통제를 효율성의 증거로 사용한다.

## 7. 만들지 않기로 결정한 것

QuickHack의 설계 역량은 구현한 기능만으로 설명되지 않는다. 정확성, 제품 목적, 복잡도와 운영 비용을 검토한 뒤 명시적으로 만들지 않은 것도 중요한 결정이다.

### 정확히 복원할 수 없는 과거 데이터

과거 외부 시각과 상태 전이 증거가 없으므로 기존 데이터를 synthetic baseline이나 현재 값으로 backfill하지 않았다.

> 정확하지 않은 과거를 만들어 통계의 신뢰 범위를 넓게 보이게 하는 대신, 이벤트 기록 이후만 신뢰 가능한 범위로 공개했다.

### 통계 목적과 맞지 않는 운영 기능

- 반품 물건의 현재 이동 위치는 통계가 아니라 운영 조회의 책임으로 분리했다.
- 현재 처리 상태는 분석 통계가 아니라 대시보드와 업무 메뉴에 남겼다.
- 기기·SKU 자유 검색은 회사 방향 판단보다 운영 조회에 가까워 통계에서 제거했다.
- 적용 기간은 workspace 안에서만 유지하고 별도 개인 설정 기능으로 영구 저장하지 않았다.

### 제한적인 운영 위험을 위한 과도한 구조

중복 송장 출력 가능성은 용지 낭비와 작업자 확인 수준의 운영 위험으로 수용했다. 외부 송장 등록과 운임 청구를 다시 실행하지 않고 포장 검증이 오출고를 차단하므로 복잡한 다중 PC 출력권·인계 시스템을 만들지 않았다.

대신 결과 불명 출력의 자동 재출력 금지와 로컬 개인정보 spool 정리는 유지했다.

### 위험한 기능을 더 포장하지 않고 공개 경계에서 제거

실행 중인 SQLite 파일을 일반 클라이언트에서 온라인 복구하는 기능은 인증을 더 추가하는 방식으로 보강하지 않았다.

- 일반 업무 UI와 공개 API에서 복구 기능 제거
- 서버 프로세스와 worker가 완전히 정지한 오프라인 경계에서만 파일 교체
- 안전 backup, 무결성 검사, 원자 교체와 rollback
- 중단 상태를 자동 추정하지 않고 운영자가 resume 또는 rollback 선택
- 기존 자동 backup worker와 실행 이력은 재사용

이 사례는 기능 추가가 아니라 **위험한 권한과 실행 경계를 축소한 설계**다.

## 8. 네 가지 핵심 설득 문장

### 숫자의 신뢰

> **숫자를 보여주는 화면이 아니라, 숫자가 신뢰될 수 있는 증거 구조를 설계했습니다.**

### 개인정보 경계

> **개인정보 삭제 시점을 단순 날짜가 아닌 실제 업무 종결 상태로 모델링했습니다.**

### 자동화의 중단 조건

> **재시도 로직뿐 아니라 자동화가 멈추고 사람에게 판단을 넘겨야 하는 조건을 설계했습니다.**

### 병렬 작업 오케스트레이션

> **기능을 의존성 기반 작업 그래프로 변환하고, 충돌하지 않는 AI 작업을 병렬화해 구현과 통합을 관리했습니다.**

## 9. 포트폴리오 페이지 권장 구성

### 첫 화면

제목:

> **AI가 코드를 만들기 전에, AI가 따라갈 시스템 지도를 만들었습니다.**

설명:

> QuickHack은 현장의 모호한 ERP 문제를 상태, 데이터 정본, 실패 경계, 자동화 책임과 작업 의존성으로 구조화하고 여러 AI 에이전트의 구현·리뷰·검증을 조율한 프로젝트입니다.

### 사례 카드

1. **숫자의 근거를 재설계하다**  
   재고 원장, latest inbound, reconciliation, lazy movement

2. **삭제 가능한 시점을 모델링하다**  
   개인정보 lifecycle, active claim, derived snapshot

3. **자동화가 멈춰야 할 때를 정하다**  
   duplicate skip, manual rebuild, read verification, review required

4. **의존성을 설계해 병렬화하다**  
   lane, wave, worktree, integration owner, independent verification

5. **만들지 않을 것을 결정하다**  
   synthetic backfill, 통계 검색, 자동 재출력, 공개 온라인 복구

### 증거 영역

- SDD 결정 기록
- React Flow 아키텍처와 데이터 흐름
- 실제 service와 schema
- 상태 전이와 실패 경로
- 전용 테스트와 전체 회귀
- 채택한 설계와 기각한 대안

## 10. 면접용 요약

### 30초 설명

> QuickHack을 처음에는 필요한 기능을 AI에게 바로 구현시키는 방식으로 만들었습니다. 프로젝트가 커지면서 같은 숫자를 화면마다 다르게 계산하거나 실패 상태를 임의로 처리하는 문제가 생겼습니다. 이후 업무 사실, 데이터 정본, 실패 경계, 자동화 중단 조건과 작업 의존성을 SDD로 먼저 구조화했습니다. 재고 원장의 숫자 근거, 개인정보 수명주기, 수동 판단이 필요한 재시도 경계를 설계하고, 독립 작업은 여러 AI 작업 환경에서 병렬로 진행하되 공유 스키마와 계약은 단일 통합 경계에서 관리했습니다. 제가 증명하려는 역량은 AI 사용 자체가 아니라, AI가 안전하고 빠르게 구현할 수 있는 작업 시스템을 설계하고 결과를 책임지는 능력입니다.

### “결국 AI가 대부분 만든 것 아닌가요?”

> 코드 생성에는 AI의 기여가 큽니다. 하지만 AI는 현장에서 어떤 숫자를 신뢰해야 하는지, 개인정보를 언제 지워도 되는지, 결과 불명 요청을 재시도해도 되는지, 어떤 기능이 과설계인지 스스로 책임질 수 없습니다. 저는 이런 제품 판단을 상태와 데이터 계약으로 만들고, 구현 가능한 PR과 병렬 작업 lane으로 분해했습니다. AI의 산출물은 코드, 테스트, 스키마, 호출 경로와 SDD를 대조해 검증했습니다. 제가 맡은 핵심 역할은 타이핑이 아니라 문제 정의, 경계 설정, 작업 오케스트레이션과 최종 검증입니다.

## 11. 이미지 초안 방향

이 문서에서 다음으로 만들 핵심 이미지는 전체 시스템 아키텍처가 아니라 **주장과 증거의 연결 지도**다.

중앙:

> **AI가 안정적으로 개발할 수 있는 시스템과 작업 지도를 설계했다.**

주변의 네 축:

1. 데이터의 진실 — 재고 원장과 reconciliation
2. 구현 가능한 책임 경계 — 개인정보 lifecycle
3. 자동화의 중단 조건 — 결과 불명, 수동 재계산과 검토
4. 의존성 기반 실행 — 병렬 lane, worktree와 integration owner

하단:

- 만들지 않은 기능
- 기각한 대안
- 코드·테스트·SDD 증거

이미지는 청사진 스타일을 사용하되 각 축에 한 문장, 대표 상태 또는 데이터 구조, 실제 근거 파일만 배치한다. 세부 설명은 본문에서 제공하고 이미지에 작은 글씨를 과도하게 넣지 않는다.

## 12. 현재 근거 상태와 작성 주의

### 구현 완료 기록이 강한 사례

- inventory ledger matrix와 공통 reconciliation
- statistics completion과 daily snapshot runtime
- 공통 외부 쓰기 `REVIEW_REQUIRED` 기반
- 코드리뷰 P1의 계정·로그인 보안 항목

### SDD에는 구현·병합 기록이 있으나 현재 checkout과 차이가 있는 사례

- CR-010 후반 client cutover
- CR-012 개인정보 lifecycle
- CR-013 파생 개인정보 snapshot 정리

현재 workspace의 `main` checkout은 위 후속 구현 branch보다 이전 revision이다. 최종 포트폴리오에서 코드 캡처와 commit 증거를 넣을 때는 해당 branch 또는 최신 병합 tree를 다시 확인해야 한다.

### 설계 사례로만 표시할 항목

- 판매 채널 재고 동기화 전체 기능은 `draft-with-open-questions`
- P2의 11개 병렬 lane은 충돌 지도와 구현 방식의 설계 근거이며 전체 구현 완료 주장이 아님

## 13. 최종 메시지

QuickHack의 핵심 성과는 화면 수나 코드의 양이 아니다.

모호한 현장 문제를 다음 시스템 언어로 바꾼 것이 핵심이다.

- 데이터의 의미와 정본
- 상태와 전이
- 실패와 결과 불명
- 자동화와 사람의 책임
- 구현 의존성과 병렬 경계
- 완료와 검증 기준

> **QuickHack은 AI가 만든 ERP가 아니라, AI가 안정적으로 개발할 수 있도록 문제와 판단, 작업 의존성을 구조화한 프로젝트다.**

그리고 이 프로젝트가 증명하려는 나의 역량은 다음과 같다.

> **나는 모호한 문제를 구현 가능한 시스템 지도로 바꾸고, 여러 AI 작업을 안전하게 병렬화하며, 그 결과가 하나의 제품 계약으로 통합되도록 통제할 수 있다.**
